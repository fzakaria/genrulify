The theory behind the genrules

Nix runs a builder that can discover its next input halfway through a command. Bazel and Buck2 want the dependencies of each action up front. A recording gives genrulify one execution in which the builder has already made those choices. The conversion target is concrete: build the same output Nix archive (NAR) for that recording.

Where does an action start?

Take a compiler driver. It may launch a compiler, an assembler and a linker. Running the driver once already launches its children. Genrulify can keep that subtree together. It groups overlapping cuts and processes that share a pipe, then compares the writable filesystem at the start and end of the group. Changes made by the driver shell between groups enter the graph as recorded values.

Each observed change to a path defines a value. A later group that reads that version gets an edge to its producer. Even if both commands open /build/bundle, the bytes before and after an append have distinct names. This is single static assignment (SSA) applied to filesystem entries.

The splice MLIR dialect

A value of type !splice.entry represents one version of one path. Its #splice.entry attribute records the path, kind, mode and modification time. A regular file carries a content hash, a symlink carries its target, and a directory's children have their own values.

Operations in a recorded build
OperationMeaning
splice.literalIntroduces entries from the recording. These include initial sandbox contents, writes between groups and results supplied from the recording when replay falls short.
splice.execConsumes the versions visible to a group and produces the versions it wrote. Its step identifies the recorded processes and their arguments, environment and working directories.
splice.outputSelects the final version of each entry under a derivation output and gives the archive rule its inputs.

Read an actual edge

In the three-command example, %0 is the build directory. The first dd produces %1. The second consumes %1 and produces %2 at the same path. The hashes below are abbreviated. 

%1 = splice.exec "dd" at 735(%0) -> [
    #splice.entry<"/build/bundle" file 644 mtime 1 "cb94740a…">
]
%2 = splice.exec "dd" at 764(%0, %1) -> [
    #splice.entry<"/build/bundle" file 644 mtime 1 "50f55425…">
]

The explorer prints the module of every recorded package this way. Point at %1 there and its definition and its use light up. Select the dd at step 764 and switch between Files, MLIR and BUILD.bazel to follow that edge into a rule. Open the example recording.

Inside a generated rule

In the patchelf build, the rule named s1274_tar unpacks the source. The last line of its cmd is the execve that was recorded, and nothing in the rule calls genrulify. 

genrule(
    name = "s1274_tar",
    srcs = [
        ":actions/s1274_tar.manifest",
        ":closure.txt",
        ":env/12.env",
        ":platform/etc/passwd",
        ":sandbox.sh",
        …
    ],
    outs = [
        "s1274_tar/build/patchelf-0.15.2/COPYING",
        "s1274_tar/build/patchelf-0.15.2/Makefile.am",
        … 66 more files
        "s1274_tar.ok",
    ],
    cmd = " ".join([
        "./sandbox.sh --in . --in $(RULEDIR) --out $(RULEDIR)",
        "--name s1274_tar --timeout 300",
        "run --cwd /build --env 12 --argv0 tar --fd 0=null --fd 1=err --fd 2=err --status 0 --argc 5 --",
        "/nix/store/5ixf6i3k…-gnutar-static-1.35/bin/tar xf /nix/store/9bangizl…-patchelf-0.15.2.tar.bz2 --mode=+w --warning=no-timestamp",
    ]),
    tags = ["no-remote"],
)

Each file version is a real file in the build system's tree, named by the rule that wrote it and its path in the build. A rule that reads /build/patchelf-0.15.2/Makefile.am as tar left it lists :s1274_tar/build/patchelf-0.15.2/Makefile.am in its srcs. A rule that reads the version a later command wrote lists that command's file. The SSA values of the module are the labels of the build file.

A recorded command only makes sense where it ran. It names /build and the output path absolutely, and it expects its environment and its descriptors. sandbox.sh is a shell script in the workspace that puts those back. It copies the declared inputs to their recorded paths under a private root, mounts that root and the store paths in closure.txt with bubblewrap, and starts the command with the environment in env/12.env. The line above the command is its wiring: working directory, argv[0], what each descriptor was, and the exit status the recording saw.

The manifest lists the kind, mode and SHA-256 of every result the rule declares. The script compares what the command left with that list before copying anything to outs, so a rule that drifts from the recording fails. A pipeline is one rule with one run line per process and a --pipe for each pipe between them. The tarball is a store path. The rule reads it from the host's Nix store, which is why the rule is tagged no-remote. Select the tar group and compare its Processes and BUILD.bazel tabs. Open the patchelf recording.

Why replay composes

Start with a literal. Its bytes come from the recording. Now pick a group whose input versions have all been produced. If those inputs match the recording, the group sees the same staged filesystem it saw during its isolated check. Assuming the group is deterministic on that filesystem and execution platform, it produces the same used results. Apply the argument down the graph and the archive rule receives the recorded output entries. Every topological ordering respects the same edges.

The checker runs surviving groups in isolation, with the script and the arguments their rules will have, and checks their exit statuses and used results. It can widen the inputs, pin individual results to recorded bytes, or replace a group with a literal. A group that needed wider inputs is replayed once under a system call tracer, and its inputs are cut back to what the trace shows it touching. MLIR's canonicalizer can remove groups whose results have no users. In the limiting case every output entry can be supplied as a literal. The explorer reports replay coverage so you can tell how much work each graph actually recomputes.

Two successful replay passes provide evidence about determinism. The proof assumes it. A matching NAR establishes output-tree equality for the fixed inputs. An edit that adds a header can change the compiler's choices and calls for a new recording.
