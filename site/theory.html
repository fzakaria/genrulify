Why this works

To compile GNU hello, GCC needs hello.c from the tarball and config.h from configure. A recording tells us which version of each file GCC read. Give GCC those files again and we can check whether it produces the same hello.o. genrulify does this for each command that the generated build will run.

How files connect commands

Rewind can return to any step in the build. genrulify compares the filesystem before and after a command to see what changed. Commands that share a pipe or overlap in time are checked together. We call the unit we replay a group.

Suppose one command writes a file and a second appends to it. Both write the same path, but the second command needs the version the first one left behind. In the build graph each version gets its own name. The second line in this example recording uses the name from the first. 

%dd_735 = splice.exec "dd" at 735(%sandbox_717)          -> […]
%dd_764 = splice.exec "dd" at 764(%sandbox_717, %dd_735) -> […]

%dd_735 names the first version of /build/bundle. It appears as an input on the second line. Giving each version a name is called single static assignment (SSA).

What one group has to reproduce

Call the filesystem at step \(t\) \(\sigma_t\). If a group \(G\) starts at step \(a\) and ends at step \(b\), the paths it changed are

\[ W(G) = \{p \mid \sigma_b(p) \ne \sigma_a(p)\}. \]

Only changes that feed another group or the final output matter. Call those paths \(U(G)\). For GCC, the linker needs the object file. A scratch file that nobody reads can be ignored.

genrulify gives the group a set of input paths \(R(G)\), with the entries they had at step \(a\). It runs the group in a sandbox on a fixed platform \(P\). Each process must exit with its recorded status, and each used result \(p \in U(G)\) must match its recorded entry.

\[ \operatorname{run}_P(G,\sigma_a|_{R(G)})(p) = \sigma_b(p). \]

The right side is what the recording says should be there. For an object file, that includes its bytes and mode. The checker requires two clean replay passes. If a group needs more files, the checker widens its inputs. If a result keeps changing, such as a timestamped log, the checker can supply the recorded entry. This is called pinning.

Why the checks add up

Suppose every group that will run passes its check. Assume also that giving a group the same inputs and platform always produces the same results. Then any build order that puts each producer before its consumers reproduces the recorded Nix archive (NAR).

Follow one file through the graph. A literal starts with the recorded entry. A copy takes bytes from an earlier file and applies the recorded metadata. By the time a command runs, each of its inputs therefore matches the version used in its check. It produces the same result again. Repeating the argument along every edge gives the recorded entries for the final archive. This is induction over the build order.

Bazel and Buck2 can run independent commands in parallel. If a group cannot replay at all, the recording can supply all its results. Even a graph made entirely of literals reproduces the archive. The timeline shows how much work each build actually repeats.

Which commands can be skipped?

A mkdir can become a constant because its directory is fully described by the recorded entry. An install that keeps the bytes of its input can become a copy with a new path and mode. A command whose results never reach the output can disappear. In each case the next reader still gets the same entry.

What a generated rule looks like

In GNU hello, the rule for hello.o names the rule that unpacked the source and the rule that wrote the configuration header. Here is an excerpt from its BUILD.bazel file in the explorer. 

cc_object(
    name = "s95245_gcc",
    src = ":s1375_tar/build/hello-2.12.3/src/hello.c",
    hdrs = [
        …
        ":s4251_bash/build/hello-2.12.3/config.h",
        …
    ],
    out = "s95245_gcc/build/hello-2.12.3/src/hello.o",
    …
)

The rule calls sandbox.sh, which puts the inputs back at the paths GCC expects, runs the recorded command line and checks the resulting object.

What happens when a source changes?

A recorded workspace checks output hashes when a rule runs. Two successful checks give us evidence that a command is repeatable. A later run can still fail if, for example, the command reads the clock.

For a live project, convert --source generates rules that read your checkout and accept new output bytes. If an edit changes which headers GCC needs, record the build again to update the graph. Build and edit the C example.
