Why this works

A build that has already run is a list of commands and the files that moved between them. Run each command again on the files it had, and you get the files it made. Do that for every command and you get the build. This page says that carefully, proves it, and shows what a generated rule looks like.

The graph

Rewind runs the build in a deterministic VM and can go back to any step of it. So for a step \(t\) we can ask what the filesystem held. Call that \(\sigma_t\): a map from paths to entries, where an entry is a file with its bytes and mode, a directory, or a symlink.

A group \(G\) is a command, or a pipeline, that ran from step \(a\) to step \(b\). Two sets describe it:

  • \(R(G)\), the paths it is given, chosen from the paths of \(\sigma_a\);
  • \(W(G) = \{\, p : \sigma_b(p) \neq \sigma_a(p) \,\}\), the paths it changed.

Every changed path gets a new value. A value is one version of one path, so a file written twice has two values and an in-place edit is an ordinary edge. This is single static assignment, on files. In the splice dialect of MLIR a build that appends to a file looks like this: 

%dd_735 = splice.exec "dd" at 735(%sandbox_717) -> [
    #splice.entry<"/build/bundle" file 644 mtime 1 "cb94740a…">
]
%dd_764 = splice.exec "dd" at 764(%sandbox_717, %dd_735) -> [
    #splice.entry<"/build/bundle" file 644 mtime 1 "50f55425…">
]

Both commands write /build/bundle. The second one reads the first one's version, %dd_735, and defines its own. Open this build in the explorer.

The four operations
OperationMeaning

splice.copyA file with the bytes of another version, under a new path, mode or time.
splice.outputThe final version of every path under a derivation output.

The check

Write \(\operatorname{run}(G, F)\) for the filesystem left by starting the recorded processes of \(G\) on a filesystem that holds exactly \(F\). Everything else a process can see is fixed: the store paths, the user, the hostname. Let \(U(G) \subseteq W(G)\) be the paths whose new value something later reads.

Check. A group \(G\) passes when its processes end with their recorded statuses and

\[ \operatorname{run}\bigl(G,\ \sigma_a|_{R(G)}\bigr)(p) \;=\; \sigma_b(p) \qquad \text{for every } p \in U(G). \]

In words: alone in a sandbox, given only its recorded inputs, the group leaves files with the recorded hashes. genrulify check runs this for every group, twice. A group that fails is given more of the tree, then has single files taken from the recording, and in the last resort becomes a splice.literal.

The proof

Write \(\operatorname{rec}(v)\) for the entry the recording holds for a value \(v\). The claim is that a build system which runs the graph computes \(\operatorname{rec}(v)\) for every value.

Theorem 1. Suppose every splice.exec passes its check and \(\operatorname{run}\) is a function of its inputs. Evaluate the graph in any order that respects its edges. Then every value \(v\) that is used evaluates to \(\operatorname{rec}(v)\). In particular each output is the recorded output, byte for byte.

Proof. By induction along the order. Take the node that defines \(v\).

  • splice.literal. Its result is \(\operatorname{rec}(v)\) by definition.
  • splice.copy of a value \(u\). The node is only built when \(\operatorname{rec}(v)\) and \(\operatorname{rec}(u)\) have the same bytes. By induction \(u\) evaluates to \(\operatorname{rec}(u)\), so the copy has the bytes of \(\operatorname{rec}(v)\). Its path, mode and time are the recorded ones.
  • splice.exec of a group \(G\). Each operand comes earlier in the order, so it evaluates to its recorded entry. The staged filesystem is therefore \(\sigma_a|_{R(G)}\), the one the check ran on. \(\operatorname{run}\) is a function, so the group leaves what it left during the check: \(\sigma_b(p) = \operatorname{rec}(v)\) for the path \(p\) of \(v\). \(\qquad\blacksquare\)

The proof uses the order and nothing else. Bazel and Buck2 may run independent rules in parallel, cache them or skip them, and the result is the same.

Theorem 2. Every recording has a graph that satisfies Theorem 1, and check finds one.

Proof. Make every group a literal. No check is left to fail. Each time a group fails, check moves it one step closer to that graph, and there are finitely many steps. \(\qquad\blacksquare\)

So the conversion cannot fail. What changes from one package to the next is how much of the build is run again and how much is carried as recorded bytes, and the explorer reports that for every package.

The passes keep it true

Theorem 1 asks one thing of a graph: every node yields the recorded entry when its operands do. A rewrite that keeps that property keeps the theorem.

Why each rewrite is safe
RewriteWhat it doesWhy the theorem still holds
Eliminate dead codeDeletes a node nothing reads.No other node's operands change, so every check stands as it was.
Fold constantsMoves directories, symlinks and empty files into a literal.A literal is the recorded entry by definition. The group has less to reproduce.
Merge, raise, linkReplaces a result that has the bytes of an existing value with a copy of it.The copy case of the proof.
Finer cutsTreats a process that only ran other commands as part of the builder.The smaller groups are checked like any others.

A generated rule

Each splice.exec becomes one genrule. This one compiles src/hello.c in GNU hello: 

genrule(
    name = "s95245_gcc",
    srcs = [
        ":s1375_tar/build/hello-2.12.3/src/hello.c",
        ":s1375_tar/build/hello-2.12.3/src/system.h",
        ":s4251_bash/build/hello-2.12.3/config.h",
        ":sandbox.sh",
        …
    ],
    outs = [
        "s95245_gcc/build/hello-2.12.3/src/hello.o",
        "s95245_gcc.ok",
    ],
    cmd = " ".join([
        "./sandbox.sh --in . --in $(RULEDIR) --out $(RULEDIR)",
        "--name s95245_gcc --timeout 300",
        "run --cwd /build/hello-2.12.3 --env 62 --fd 0=null --fd 1=err --fd 2=err --status 0 --argc 55 --",
        "/nix/store/5q6bdxkp…-gcc-16.2.0/bin/gcc … -g -O2 -c -o src/hello.o src/hello.c",
    ]),
    tags = ["no-remote"],
)

The last line of cmd is the execve that was recorded. The srcs are the file versions the compiler opened, named by the rule that wrote each one: hello.c as tar unpacked it, config.h as configure wrote it. The values of the graph are the labels of the build file.

A recorded command only makes sense where it ran. It names /build, and it expects its environment and its file descriptors. sandbox.sh is a shell script that ships in the workspace and puts those back. It copies the inputs to their recorded paths, runs the command, and compares every output with the recorded hash before handing it on. That comparison is the check above, so a rule that stops reproducing the recording fails. genrulify is not needed to build the workspace.

Open hello in the explorer, pick a gcc node and compare its Processes and BUILD.bazel tabs.

What it does not say

  • One build, one graph. The graph recomputes the build that was recorded. Edit a source file and the compiler may open other headers. That is a new build, and it needs a new recording.
  • Determinism is assumed, then sampled. The proof takes \(\operatorname{run}\) to be a function. Two passing replays are evidence for that. Every rule checks its own outputs on every build, so a command that later drifts fails its rule.

The model of tasks, a store and a scheduler is from Build Systems à la Carte. In its terms, a recording turns a build's dynamic dependencies into static ones, which is why they can be written down as srcs. The longer note spells that out, and Splice.td defines the dialect.
